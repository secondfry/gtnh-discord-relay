# Event hooks for GTNH 2.9.0

The [GTNH 2.9.0 manifest](https://github.com/GTNewHorizons/DreamAssemblerXXL/blob/2b06bec/releases/manifests/2.9.0.json) lists BetterQuesting 3.8.92-GTNH and ServerUtilities 2.4.22. These versions were confirmed in the official [GTNH 2.9.0 stable Java 17–26 server ZIP](https://www.gtnewhorizons.com/version-history/).

- BetterQuesting posts [`QuestEvent`](https://github.com/GTNewHorizons/BetterQuesting/blob/3.8.92-GTNH/src/main/java/betterquesting/api/events/QuestEvent.java) on `MinecraftForge.EVENT_BUS` from its [server-side completion check](https://github.com/GTNewHorizons/BetterQuesting/blob/3.8.92-GTNH/src/main/java/betterquesting/handlers/EventHandler.java#L195-L242). Check for `COMPLETED`, skip empty sets and respect `NativeProps.SILENT`. On the server, the event's player UUID matches the player's [game profile UUID](https://github.com/GTNewHorizons/BetterQuesting/blob/3.8.92-GTNH/src/main/java/betterquesting/api/api/QuestingAPI.java#L35-L55).
- ServerUtilities updates `afkTime` in its [END tick handler](https://github.com/GTNewHorizons/ServerUtilities/blob/2.4.22/src/main/java/serverutils/handlers/ServerUtilitiesServerEventHandler.java#L197-L275). Its notification tracks crosses of `ServerUtilitiesConfig.afk.getNotificationTimer()`, ignoring fake players and suppressing in-game announcements for vanished players. The same handler logs vanished players' AFK transitions, so reading the log alone would expose them.
- ServerUtilities cancels [muted or disallowed chat](https://github.com/GTNewHorizons/ServerUtilities/blob/2.4.22/src/main/java/serverutils/handlers/ServerUtilitiesServerEventHandler.java#L94-L107) at `HIGHEST` priority when its rank chat override is active. Listen at `LOWEST` without receiving canceled messages.
- ServerUtilities applies some vanish rules at the vanilla broadcast call, after the Forge event. The relay checks the same vanished-player state before forwarding events. Its chat hook honors the player's ServerUtilities option to allow public chat while vanished. [ServerUtilities vanish mixins](https://github.com/GTNewHorizons/ServerUtilities/tree/2.4.22/src/mixins/java/serverutils/mixins/early/minecraft/vanish)
- The stable 2.9.0 server ZIP's 216 mod JARs contain no class referencing `showDeathMessages`. The relay forwards deaths when that rule is absent and honors an explicit rule if a server provides one.
- FML's [server run loop patch](https://github.com/MinecraftForge/FML/blob/1.7.10/patches/minecraft/net/minecraft/server/MinecraftServer.java.patch#L23-L81) calls `handleServerStopping()` after normal loop exit and `handleServerStopped()` in the final cleanup for normal exits, startup failures and exceptions. A running server that reaches the stopped event without a stopping event ended unexpectedly. A process killed outside Java or a hard JVM failure can bypass these callbacks entirely.
- The [ServerUtilities pause mixin](https://github.com/GTNewHorizons/ServerUtilities/blob/2.4.22/src/mixins/java/serverutils/mixins/early/minecraft/MixinMinecraftServer_PauseWhenEmpty.java#L50-L84) can skip both FML tick events while an empty server keeps handling connections. The relay timestamps both calls to `tick()` from `MinecraftServer.run()` to detect genuine stalls during pauses. The [ServerUtilities watchdog](https://github.com/GTNewHorizons/ServerUtilities/blob/2.4.22/src/main/java/serverutils/watchdog/ServerHangWatchdog.java#L43-L105) can forcibly exit on `max-tick-time`, so hang delivery depends on detecting and reporting the stall before shutdown.
- AdvancedBackups is not part of GTNH 2.9.0; the relay was built against the [secondfry fork v4.3.0](https://github.com/secondfry/AdvancedBackups/releases/tag/v4.3.0). It sets `ABCore.clientContactor` in `FMLServerStartingEvent`, and its `BackupTimer` calls `handle()` from the server tick only when `logging.clients` is not `none`, re-sending the current status instance. The relay wraps that contactor in `FMLServerStartedEvent`, delegates every call unchanged and posts each start, completion, failure and cancellation once per status instance. Progress is not relayed. `ThreadedBackup.lastStats` exists only in the fork, so upstream builds post completion without stats. Shutdown backups publish no status at all, so they are not relayed.
